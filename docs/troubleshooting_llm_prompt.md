# 🛠️ LLM 역량 평가 분석 엔진 고도화 트러블 슈팅 보고서

이 보고서는 GitMate의 핵심인 AI 역량 평가 지표에서 관찰된 '점수 인플레이션' 및 '주관적/추상적 평가 근거' 문제를 해결하고, 실제 기업의 수석 아키텍트 수준의 날카롭고 신뢰도 높은 엔지니어링 피드백을 제공하도록 프롬프트를 고도화하고 시스템을 안정화한 트러블 슈팅 과정을 상세히 기록한 문서입니다.

---

## 1. 개요 (Overview)

### 🚨 문제 정의
1. **점수 인플레이션 (Score Inflation) 현상**:
   * 개발자의 아주 기본적인 소통 활동(예: Git 충돌 방지를 위한 소통 약속, 기본적인 PR 템플릿 채우기, 일반적인 버그 수정 등)에 대해 너무 쉽게 만점(5.0점)을 남발하여 변별력이 극도로 저하되었습니다.
2. **추상적이고 뻔한 칭찬 (`reason` 필드)**:
   * 평가 대상이 되는 개발자가 납득할 수 있는 구체적인 객관적 근거 없이 `"~하는 모습이 훌륭하게 보입니다"`, `"변경 사항을 명확히 설명하고 있습니다"` 등 주관적인 미사여구와 수식적 표현에 치우쳐 있어 평가의 신뢰도를 저하시켰습니다.
3. **영양가 없는 평이한 개선점 제시 (`improvement` 필드)**:
   * `"앞으로도 이 코멘트 습관을 꾸준히 유지하세요"`, `"더 구체적으로 코드를 작성해 보세요"` 등 실질적인 기술적 성장에 도움을 주기 힘든 형식적인 멘트들이 반복해서 출력되었습니다.

### 💻 배경 상황
* **환경**: NestJS (백엔드) + OpenAI GPT-4o API 기반 아키텍처
* **대상 컴포넌트**: [llm-provider.service.ts](file:///Users/chasuyeon/workspace/git-mate-backend/src/analysis/llm-provider.service.ts)
* **영향성**: 데이터베이스나 세션 연결이 끊기거나, 혹은 LLM의 모호한 응답 형식으로 인해 분석 파서 단계에서 오동작을 유발할 위험이 있어 높은 정밀성이 지속적으로 요구되었습니다.

## 2. 접근 방법 (Approach)

### 🔍 원인 분석
1. **프롬프트 내 채점 Rubric의 모호성**:
   * 기존 프롬프트에는 1점, 3점, 5점 단위의 평가 가이드라인만 단순 텍스트로 나열되어 있어, LLM이 해피 패스(Happy Path) 위주로 대충 해석하여 4.5점~5.0점 고득점을 성급하게 부여하고 있었습니다.
2. **증거 추적 제약 조건 누락**:
   * LLM에게 제공되는 GitHub 풍부한 활동 데이터(PR, 커밋 로그, 리뷰 대화 등)에서 특정 증거(Citations)를 가져오도록 강제하는 규칙이 없었습니다. 이로 인해 LLM은 제공된 데이터를 종합적으로 추상화한 뒤 주관적으로 뭉뚱그려 평가했습니다.
3. **HR 전문가 페르소나의 느슨함**:
   * 단순 기술 HR 멘토 페르소나로 설정되어 있어 평가 기준이 부드럽고 칭찬 일변도였습니다. 15년 차 이상의 엄격한 수석 아키텍트(Principal Engineer)와 같은 강력한 피어 리뷰어 페르소나가 결여되어 있었습니다.

### 💡 가설 설정 및 검증 계획
* **가설 1**: 채점 기준표(Rubric)에 명시적인 점수대별 문턱(Gatekeeping)을 구축하고, 특별한 아키텍처적 기여의 증거가 데이터상으로 명확히 관찰되지 않을 경우 **기본 점수(Meets Expectation: 3.0~3.5)**로 강제 수렴하게 만들면 점수 인플레이션을 방지할 수 있을 것이다.
* **가설 2**: 응답 필드(`reason`, `improvement`, `example`)의 작성 포맷을 엄격하게 제한하여, `[증거: PR #번호 / 커밋해시]`의 강제 적시, 백엔드 기술의 '태생적 한계 및 트레이드오프(Trade-off)' 분석, 그리고 실제 처방 가능한 '디자인 패턴 및 기술 키워드' 작성을 의무화하면 주관적 수식어를 100% 억제할 수 있을 것이다.

## 3. 해결 방안 (Solution)

### 🛠️ 조치 사항

#### A. 수석 백엔드 아키텍트(Principal Engineer) 페르소나 및 채점 루브릭 이식
[llm-provider.service.ts](file:///Users/chasuyeon/workspace/git-mate-backend/src/analysis/llm-provider.service.ts)의 `buildSystemPrompt()`를 전면 개정하여 다음 규칙들을 프롬프트 시스템에 강력하게 주입했습니다.

```typescript
// 엄격한 채점 루브릭 (Score Rubric) 설계
- 1.0 ~ 2.5 (Below Expectation): 비협조적 소통, 맥락 없는 코드 제출, 비효율적인 설계 방치로 시스템적 취약점 노출.
- 3.0 ~ 3.5 (Meets Expectation - 기본값): 일반적인 개발자의 당연한 수준의 일상적 액션 (충돌 사전 회피 조율, 통상적 버그 픽스 등). 데이터상 특출난 엔지니어링적 임팩트 증거가 없다면 **무조건 이 구간을 기본값으로 강제 부여**.
- 4.0 ~ 4.5 (Above Expectation): 도메인의 태생적 한계 극복, 인프라 트레이드오프 인지 하에 정량화된 벤치마크 및 리팩토링으로 팀 생산성을 극대화한 증거가 확보될 경우.
- 5.0 (Outstanding - 극도로 제한): 대규모 전사 장애 방어, 팀의 핵심 아키텍처 패러다임 전환 등 테크 리더로서의 독보적 업적이 텍스트 증거로 직접 입증될 때만 극히 드물게 부여.
```

#### B. 출력 포맷 및 필드 규칙의 강제화 (뻔한 조언 원천 금지)
* **`reason`**: 주관적 칭찬 금지. 반드시 분석 대상 데이터 내의 **`[증거: PR #번호 / 커밋해시]`**를 명시하고, 백엔드 엔지니어링 용어(예: 동시성 제어, 쿼리 튜닝 등)를 차용해 아키텍처적 임팩트를 객관적 팩트로 논증하도록 설계했습니다.
* **`improvement`**: 단순 칭찬 및 일반론 금지. 피평가자가 차용한 기술의 **'태생적 한계'** 또는 **'인프라/성능상 트레이드오프(Trade-off)'**를 예리하게 짚어내고, 더 높은 아키텍처적 극복 과제를 단 한 문장으로 엄격히 권고하도록 제한했습니다.
* **`example`**: 다음 작업 시 직접 복사/적용해 볼 수 있는 **구체적인 디자인 패턴, 가용성 키워드, 모범 코드 조각**을 행동 지침으로 즉시 처방하게 명시했습니다.

#### C. 백엔드 Types 컴파일 오류 정교화 (Side Effect 처리)
* 프롬프트 반영 후 Typescript 컴파일 검사 단계에서, 로컬에 `@prisma/client` 타입이 생성되지 않아 PrismaService 관련하여 17개의 억울한 정적 빌드 오류가 발견되었습니다.
* `npx prisma generate` 명령어를 백엔드에 연동 기동하여, 로컬 타입들을 완전 무결하게 생성 및 원상 복구해 `npx tsc --noEmit`이 경고 0개 상태로 빌드 통과하도록 안정화했습니다.

### 🧐 해결 근거
* **결정론적 채점**: LLM이 높은 점수를 주기 위해서 반드시 "기술적 트레이드오프를 극복한 증거"를 논증해야 하므로, 근거가 부실한 고득점 남발 현상이 완벽하게 필터링됩니다.
* **텍스트 구속력**: 대괄호(`[...]`)와 쌍따옴표(`"..."`)를 동원한 실제 데이터 텍스트 인용을 필수로 강제했으므로, AI의 창작(Hallucination)에 근거한 모호한 칭찬 대신 100% 신뢰할 수 있는 실증 증적 기반의 보고서가 보장됩니다.
