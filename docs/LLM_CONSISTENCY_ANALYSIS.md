# [기술 분석 보고서] LLM 분석 일관성 향상을 위한 아키텍처 제안

## 1. 개요
현재 `git-mate` 서비스의 핵심 기능인 LLM 기반 개발 역량 분석은 결과의 비결정성(Non-determinism)으로 인해 매 실행 시 점수와 평가 근거가 달라지는 리스크가 있습니다. 이를 해결하기 위해 사용자가 제안한 **"다중 요청 후 결과 병합"** 방식과 그 외 대안들을 기술적/경제적 관점에서 분석합니다.

---

## 2. 제안 방식 분석: 다중 요청 및 병합 (Ensemble)

### 2.1 주요 장점
- **통계적 안정성:** 여러 번의 결과를 평균 내거나 최빈값을 선택함으로써 특정 회차에서 발생하는 이상치(Outlier)를 제거할 수 있습니다.
- **분석의 깊이 향상:** LLM이 매번 다른 PR의 디테일에 주목할 수 있으므로, 결과들을 합쳤을 때 더 풍부한 인사이트 제공이 가능합니다.
- **신뢰도 구축:** 사용자에게 "수차례 검증된 분석 결과"임을 어필하여 서비스의 신뢰도를 높일 수 있습니다.

### 2.2 리스크 및 단점
| 항목 | 상세 내용 | 위험도 |
| :--- | :--- | :--- |
| **비용 (Cost)** | 요청 횟수에 비례하여 OpenAI API 비용이 선형적으로 증가 (예: 3회 요청 시 3배 비용) | **High** |
| **지연 시간 (Latency)** | 병렬 처리하더라도 전체 분석 시간이 증가하며, 특히 결과 병합(Summarization) 단계가 추가될 경우 더 길어짐 | **Medium** |
| **타임아웃 (Timeout)** | AWS Lambda 환경에서 실행 시간이 30초 이상 지속될 경우 타임아웃 발생 위험 | **Critical** |
| **Rate Limit** | 짧은 시간 내에 대량의 토큰을 여러 번 사용하므로 OpenAI 계정의 분당 토큰/요청 제한에 걸릴 수 있음 | **Medium** |

---

## 3. 대안 및 최적화 전략 (Roadmap)

사용자의 제안을 포함하여, 비용 효율성을 고려한 단계별 적용 방안을 제안합니다.

### Step 1: 파라미터 및 프롬프트 최적화 (저비용/고효율)
다중 요청을 보내기 전, 단일 요청의 품질을 고정하는 것이 우선입니다.
- **Temperature 조절:** `temperature`를 `0` 또는 `0.1`로 설정하여 창의성을 배제하고 일관성을 극대화합니다.
- **CoT (Chain-of-Thought):** JSON 결과 출력 전, `reason`을 먼저 작성하게 하여 논리적 추론 후에 점수를 매기도록 유도합니다.
- **Few-Shot Prompting:** 각 점수(1, 3, 5점)에 해당하는 실제 코드 리뷰 예시를 프롬프트에 포함하여 평가 기준을 명확히 합니다.

### Step 2: 제한적 다중 요청 (병렬 실행)
Step 1 이후에도 변동성이 클 경우 적용합니다.
- **Parallel Execution:** `Promise.all`을 사용하여 N번의 요청을 동시에 보냅니다.
- **Weighted Average:** 점수는 평균을 내되, 소수점 둘째 자리에서 반올림하여 일관된 지표를 제공합니다.

### Step 3: 최종 결과 요약 (Reduce)
N개의 문장형 평가들을 하나로 합치는 단계입니다.
- **Best Selection:** N개 중 가장 신뢰도가 높은(또는 가장 긴) 문장을 선택하거나, 저렴한 모델(GPT-4o-mini 등)을 사용하여 N개의 요약본을 하나로 합치는 프로세스를 추가합니다.

---

## 4. 아키텍처 적용 시 주의사항

### 4.1 토큰 차감 로직
현재 `AnalysisService`는 LLM 사용량만큼 실시간으로 토큰을 차감합니다. 만약 3번 요청한다면 사용자의 토큰이 3배로 차감되어야 하므로, 이에 대한 사용자 고지 및 UI 업데이트가 필요합니다.

### 4.2 인프라 제약 (Lambda)
현재 프로젝트가 AWS Lambda를 사용하고 있으므로, 실행 시간이 29초를 넘지 않도록 관리해야 합니다. 다중 요청 시 응답 지연이 발생할 경우를 대비하여 `BullMQ`를 통한 비동기 처리가 필수적으로 유지되어야 합니다.

---

## 5. 최종 권장안

분석 결과의 일관성 문제는 반드시 해결해야 할 리스크이나, **단순 다중 요청은 비용 부담이 큽니다.** 따라서 다음과 같은 순서로 진행하는 것을 권장합니다.

1.  **우선 순위:** `temperature: 0` 설정 및 프롬프트 내 **'이유(Reason) 선(過) 출력 후 점수 출력'** 구조로 변경하여 1회 요청의 신뢰도를 먼저 테스트합니다.
2.  **확장 단계:** 1번으로 해결되지 않을 경우, 중요도가 높은 지표(Seniority 등)에 대해서만 2~3회 반복 분석을 실시하고 평균값을 취합니다.

---
> [!TIP]
> **비용 절감 팁:** 분석할 PR 데이터가 많을 경우, 모든 PR을 다 보내지 않고 핵심적인 내용을 담은 PR들만 샘플링하여 보내는 것만으로도 변동성을 줄이고 비용을 절약할 수 있습니다.
